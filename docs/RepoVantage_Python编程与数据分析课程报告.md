# GitHub开源项目数据分析与技术选型辅助系统：面向通用仓库的活动分析、比较与机器学习评估平台

《Python编程与数据分析》课程项目报告（Markdown 草稿）

> 封面上的专业、方向、班级、学号、姓名和指导教师信息由作者本人补充。本报告以 GitHub开源项目数据分析与技术选型辅助系统当前代码、数据包与模型评估文件为依据。系统定位为通用型 GitHub 仓库分析工具，不对应某一行业或单一业务领域；文中的课程模型结果也只适用于其固定研究样本和口径。

## 摘要

开源项目的公开活动记录分布在仓库资料、提交历史、Issue、Pull Request 和 Release 等对象中。Star 数或单项活动总量只能呈现项目的一面，无法同时说明开发节奏、协作情况、数据覆盖和观察窗口。GitHub开源项目数据分析与技术选型辅助系统将这些信息汇集到一个通用的 GitHub 仓库分析平台中，支持建立仓库库和自定义分组、采集并归档公开活动、查看单仓近期情况，以及按统一时间口径比较候选仓库。平台面向多种类型的公开仓库，不限定行业，也不依赖特定领域的术语、标签或判定规则。

项目使用 Python 完成数据清洗、统计和机器学习流程。所有时间边界统一按 UTC 处理，并分别标记真实零值、部分覆盖、未采集、失败和样本不足，防止未知值被误记为零。分析指标包括 Commit 活动、Issue 关闭、PR 合并和正式 Release 节奏。比较页面可同时查看 2–5 个仓库的归一化雷达图、可调权重的相对排名和近期维护摘要。机器学习研究基于版本化的 300 仓库历史资料，包含两个任务：使用 K-Means 归纳近期维护模式，使用逻辑回归将未来四周 Commit 活动趋势分为三类。独立的模型观测台展示训练过程和留出评估，说明这些结果属于研究评估，不是生产质量认证。

M1 使用 150 个仓库训练，并在另外 150 个留出仓库上评估，三簇的留出轮廓系数为 0.523。M2 留出集的 Macro-F1 为 0.541，平衡准确率为 0.579，均高于本轮设置的两类基线。这些结果表明模型能在现有样本中识别一定的结构差异，但样本不是 GitHub 全体仓库的随机抽样，且前期研究使用过这 300 个仓库及部分历史窗口。因此，这次评估不能视为全新的外部前瞻验证。平台呈现可追溯的活动证据和研究模型信号，项目用途、代码质量、安全性和社区状况仍需人工判断。

**关键词：** Python；GitHub；开源仓库；数据采集；数据质量；数据可视化；K-Means；逻辑回归

## 1 引言

### 1.1 研究背景

开源仓库承载代码、协作和软件发布。仓库页面会显示 Star、Fork、提交和版本等信息，但这些数字可能对应不同时间点、统计范围和对象类型。使用者筛选技术方案、观察项目活动或比较同类仓库时，单项指标往往不足以解释实际情况：短期提交量增加可能由一次集中迁移造成，Release 较少可能与滚动发布方式有关，Issue 关闭时间也会受到问题类型、维护流程和采集范围影响。

采集质量也会影响分析结果。GitHub API 分页返回数据，采集过程可能受页数预算、速率限制和数据变动影响。把未采集、请求失败或部分返回记作零，会将“缺少观测”误解为“没有活动”；直接比较不同观察窗口的数据，也可能把时间差异当成项目差异。平台因此需要在展示指标的同时说明时间范围、样本量和覆盖状态。

本系统将公开 GitHub 仓库作为分析对象，以可访问的仓库资料和活动记录为输入，生成可筛选、比较和追溯的统计摘要与图表。仓库无需属于特定编程语言、行业或产品类型。课程研究数据集用于验证数据处理和机器学习流程，其样本范围不等同于平台的支持范围。

### 1.2 研究目标

项目将 Python 编程、数据工程、统计分析、机器学习与 Web 应用开发整合为可运行、可复核的系统，目标包括：

1. **实现公开仓库资料管理。** 支持搜索、添加、分组、更新和移除仓库，并保留通用的仓库名称、描述、主语言、主题和基础指标。
2. **建立分模块的数据采集链路。** 将 Commit、Issue、Pull Request 和 Release 等数据按来源、时间和覆盖状态记录，支持查看采集任务进度与失败信息。
3. **形成一致的统计口径。** 对时间窗口、UTC 周界、数据去重、有效样本和缺失状态做明确约定，减少跨页面的口径漂移。
4. **支持单仓分析与多仓比较。** 提供活动趋势、处理耗时、发布节奏、近期维护摘要以及 2–5 个仓库的横向比较。
5. **训练并评估研究模型。** 对近期维护模式聚类和近期活动趋势分类分别训练、验证和留出评估，展示模型适合的诊断图表与性能指标。
6. **保证本地可运行和材料可复现。** 以统一启动命令运行后端、采集 Worker、普通用户工作台和机器学习观测台；区分固定研究资料与用户本机动态数据。

### 1.3 平台定位与适用范围

本系统面向不同用途的公开 GitHub 仓库，提供信息组织、时间序列、质量状态、比较和可视化能力。这里的“通用”指分析基于相对稳定的仓库与活动对象，不要求用户配置特定行业的本体或判定规则。

| 定位维度 | 当前设计 |
|---|---|
| 分析对象 | 可通过 GitHub 公开接口访问的公开仓库及其可见活动记录 |
| 面向对象 | 个人开发者、技术团队、课程使用者及需要筛选候选项目的研究者 |
| 通用能力 | 仓库管理、分组、Commit/Issue/PR/Release 分析、维护摘要、比较、导出 |
| 领域依赖 | 当前不要求仓库属于某个行业；不依赖医疗、金融或其他领域专用知识图谱 |
| 数据源边界 | 当前采集连接器针对 GitHub；“通用”不代表已经兼容 GitLab、Gitee 等其他托管平台 |
| 模型边界 | 研究模型只基于固定课程样本和指定特征工作；不代表适用于所有语言、规模和项目阶段 |

用户可通过仓库分组整理候选对象并标注比较语境。分组属于可编辑的组织信息，不是模型推断的项目用途分类。对比集合跨越多个分组、含有未分组仓库或使用不同主语言时，平台会提醒用户确认项目用途是否相近。即使指标可以计算，也仍需判断这些项目的目标和开发模式是否适合直接排名。

### 1.4 使用者与典型场景

## 2 总体设计

### 2.1 技术路线

项目由一个代码仓库、一个后端和两套前端组成。后端使用 Python 3.12、FastAPI、SQLAlchemy、SQLite 和 Alembic；普通用户工作台使用 Vue 3、TypeScript、Vite 和 AntV G2。独立的 Python Worker 执行采集任务，另一套 Vue 应用作为机器学习观测台，读取后端提供的固定评估数据。两套前端共享后端的数据与接口，同时分别服务日常仓库分析和模型评估。

| 技术或部件 | 在项目中的作用 |
|---|---|
| Python 3.12 | GitHub 数据处理、指标计算、模型训练、API 和采集 Worker |
| FastAPI | 仓库、分析、比较、任务、导出和模型评估接口 |
| SQLite | 本地运行时仓库信息、采集任务、规范化事件与分析结果 |
| SQLAlchemy / Alembic | 数据访问模型与数据库结构迁移 |
| Vue 3 / TypeScript / Vite | 普通用户工作台和机器学习观测台 |
| AntV G2 与自定义 SVG | 多类统计图和仓库比较雷达图 |
| scikit-learn | K-Means 聚类、标准化、逻辑回归及离线评估 |
| 独立 Worker | 执行耗时 GitHub 分页采集、进度维护和任务恢复 |

数据流程从 GitHub 公开 API 或固定数据包开始。采集器按页读取原始记录并保存请求边界，Worker 将事件映射到统一字段；质量模块检查完整性、有效样本和异常，分析服务再按既定窗口计算指标。FastAPI 返回结果及其解释信息，两个前端分别以图表和数值呈现。模型训练使用带哈希和切分清单的固定周级资料，单独生成候选模型、留出预测和评估 JSON。

### 2.2 运行形态与接口边界

完整项目提供两个本机浏览器入口。普通用户工作台默认使用 8501 端口，通过 FastAPI 提供仓库管理、单仓分析、项目比较、任务和设置功能。机器学习观测台默认使用 8502 端口，用于查看离线模型拟合与留出评估。两套页面连接同一后端，承担不同用途；8502 展示的是静态研究材料，不是生产模型的实时监控平台。

在项目根目录运行以下命令，启动器会准备前端构建、升级本地数据库，并启动 API、Worker 和两套页面：

> uv run --locked --all-extras python -m scripts.start

GitHub Token 为可选配置。未配置时可使用匿名公开接口，但会受到较低的请求速率限制。内部 API Key 与本地环境变量不应暴露给浏览器或提交到仓库。

### 2.3 数据来源与样本范围

系统区分在线运行数据、固定课程数据和模型实验数据。这些资料的时间范围、用途与观察单位不同，不应合并成一个口径不明的“总数据集”。

| 数据材料 | 样本与时间范围 | 用途 | 主要限制 |
|---|---|---|---|
| 在线 GitHub 采集 | 当前用户加入的公开仓库；随采集时间和页数预算变化 | 用户日常仓库分析、比较和维护摘要 | 受 API 额度、端点语义、分页上限和采集时点影响 |
| course-research-300-v1 周级快照 | 300 个仓库，最近 12 个完整 UTC 周，共 3,600 条仓库周记录；2026-08-10 至 2026-11-02 UTC | 近期活动演示及课程数据分析 | 历史快照；不是 GitHub 全体随机样本 |
| course-research-events-300-v1 事件快照 | 300 个仓库；窗口 2025-10-04 至 2026-11-05 UTC，采集截止 2026-11-05 10:31:37 UTC | 单仓事件趋势、关闭/合并耗时、Release 分析与比较 | Issue 仅覆盖 2025-11-03 起创建的记录；个别模块有部分或失败覆盖 |
| repo-evaluation-2026-v1 模型源数据 | 300 个仓库，每个仓库 52 周，共 15,600 条仓库周记录 | M1、M2 特征构造、训练和仓库级留出评估 | 既有历史聚合数据；150/150 是固定仓库切分，不是新采集的外部测试样本 |

课程事件快照记录了 445,175 条 Commit、167,248 条 Issue、331,723 条 Pull Request 和 42,458 条 Release。12 周快照中，Commit 周有 3,600 条记录处于完整或真实零值状态；PR 合并周有 3,588 条完整或真实零值记录，另有 12 条因并发数据变化被标为部分覆盖。完整或真实零值 Commit 周对应 125,246 次提交；完整或真实零值周中的 PR 合并数为 64,800，PR 创建数为 104,247。以上为固定数据包统计，不应误读为在线用户本机数据库的实时总量。

事件包已匿名化提交账号，也不包含 Commit message、Issue 标题与正文或 PR 标题与正文。Issue 数据从既定采集起点开始，不能覆盖仓库整个生命周期。动态数据库和在线归档保存在用户本机；版本库则保留冻结研究数据及模型复现所需材料。

### 2.4 数据预处理与质量控制

时间统一与分桶方面，后端将 GitHub 时间转换为 UTC，API 时间使用 ISO 8601 的 Z 时区形式。统计区间采用左闭右开规则，包含起始时刻，不包含结束时刻。自然周从周一 00:00 UTC 开始。采集窗口边界上的不完整周不计入完整周趋势。

事件规范化时，Commit、Issue、Pull Request 和 Release 保留各自来源对象的标识、时间、状态和仓库关系。Commit 按仓库内 SHA 去重；Issue 关闭时间与 PR 合并时间使用各自的事件字段。规范化记录支持重复处理，任务重试不会因此写入重复事件。

只有来源覆盖完整、且计数确认为零时，零值才表示该窗口没有观测到事件。其他状态按下表分别处理：

| 状态 | 含义 | 进入统计的方式 |
|---|---|---|
| complete coverage / ready quality | 查询范围达到预期，且该指标已有可用输入 | 可按指标规则进入分析；ready 不代表 GitHub 全历史完整 |
| true_zero | 查询覆盖完整，窗口内确认为零条事件 | 作为真实零值进入计数型指标 |
| partial | 有观测值，但分页或采集期间数据变化导致覆盖不完整 | 保留已观测下界和状态，不伪装成完整总体 |
| missing / not_collected | 尚未采集或没有可用输入 | 为空并解释原因，不补零 |
| failed | 来源端点失败且没有可用记录 | 标记失败，不生成虚假的零值 |
| insufficient_samples | 覆盖完整但样本不足以支持该统计量 | 显示样本不足；按指标规则不计算分位或间隔 |

耗时指标会排除缺少起始或结束时间、耗时为负及不适用的记录，并报告有效样本数和排除情况。部分采集可以展示已观察到的事件数，但不能代表完整总量。Commit、Issue、PR 和 Release 分别维护覆盖状态；某个模块失败时，其他模块的完整结果仍可用。

### 2.5 指标定义与比较口径

| 指标 | 当前统计规则 | 解释注意事项 |
|---|---|---|
| 每周 Commit | 默认分支可见提交按 UTC 周聚合，包含合并提交；同仓库按 SHA 去重 | 表示观测期提交活动，不代表代码质量、开发者人数或项目价值 |
| 最近四周变化 | 对最近八个已结束完整 UTC 周分成前后各四周，比较总数和变化率 | 是短期环比；不足八周或基期为零时不计算相应比较值 |
| Issue 关闭量 | 按可观测 closed_at 落入查询窗口的 Issue 统计；排除 Pull Request | 事件计数分母受来源覆盖范围限制 |
| Issue 关闭耗时 | 查询窗口内 closed_at 减 created_at，单位小时 | 代表最近可观测关闭耗时，不代表首次响应时间或维护者实际工时 |
| PR 合并量 | 按 merged_at 落入查询窗口的 Pull Request 统计 | 采集数据按 closed PR 来源语义处理，不等于全部新建 PR 的合并率 |
| PR 合并耗时 | merged_at 减 created_at，单位小时，仅对已合并且时间有效的 PR 计算 | 不表示所有 PR 的结案速度，也不等于创建 cohort 的转化率 |
| Release 数量与节奏 | 统计已发布正式 Release；草稿排除，预发布单列；正式版本按 published_at 排序计算间隔 | 纯 Git Tag 不算 Release；少于两次正式发布时无法计算相邻发布间隔 |
| 有效周占比 | 已有完整可用周数除以选定周数 | 描述覆盖质量与活动周观察比例，不是项目质量评分 |
| Stars、Forks、仓库年龄 | 按实际资料快照展示，不从活动总量推算 | 基础资料的采集时点可能与活动窗口不同 |

分位数按 NumPy linear 规则计算：P50 至少需要一个有效样本，P75 至少需要五个，P90 至少需要十个。Issue 和 PR 耗时分布采用固定小时区间，同时记录有效样本数、排除的无效耗时数和缺失率。端点语义会影响不同统计的纳入范围：创建时间异常的记录可能无法计算耗时，但仍可能是有效关闭事件。因此，事件数与耗时样本数可能不同。

比较页面提供同期窗口和各仓库独立窗口两种模式。同期比较取实际观察窗口的交集重新计算，且有效交集必须达到所选窗口的 80%；Commit 周均值只纳入共同完整的 UTC 周。独立窗口用于查看各仓库自身近期情况，不能作为严格的同期排名。不同分组或主语言的仓库仍可一起查看，平台会提示用途或技术栈差异，由用户判断是否适合比较。

### 3.2 主要实现步骤

1. **建立仓库目录。** 用户通过 GitHub 搜索或仓库地址添加公开仓库。系统保存仓库 ID、全名、描述、语言、主题、创建时间和最近推送时间等资料；用户也可以创建分组来整理候选仓库。
2. **登记采集任务。** 后端创建任务并确定需要采集的模块、分析时间范围和页数预算。任务列表和任务详情分别提供总体状态与模块级状态。
3. **由 Worker 执行分页采集。** Worker 调用 GitHub 接口读取公开活动数据，将 API 限制、分页完成情况、可见记录数和错误分别记录。长任务按模块维护进度和检查点，使失败或重试具有可追踪依据。
4. **规范化并持久化事件。** 各类原始字段转换到内部统一结构，按外部对象 ID 幂等写入。归档记录与数据库事件配合，保留必要的复核来源。
5. **计算版本化指标。** 分析服务依据固定的 UTC 时间窗口生成 Commit 周序列、Issue / PR 耗时分布、Release 事件及质量摘要，保存数据版本、运行时间、样本量和窗口边界。
6. **通过 API 提供结果。** 后端提供仓库、事件、比较、质量、导出和模型评估接口；前端读取同一组权威结果，避免界面和 CSV 使用不同统计口径。
7. **呈现解释和状态。** 页面同时显示图表、数值、样本数、覆盖说明和适用范围。数据不足时给出具体原因，避免空白曲线或补零引起误读。

### 3.4 机器学习分析方法

#### 3.4.1 M1：近期维护模式聚类

M1 的目标是在近期 Commit 行为中寻找活动模式相近的仓库。样本使用每个仓库最近 12 周的周级数据，构造以下五项特征：

| 特征 | 计算含义 | 解释方向 |
|---|---|---|
| 活跃周占比 | 12 周中 Commit 大于零的周数比例 | 越高表示近期有 Commit 的周更多 |
| log Commit 波动 | 对 Commit 周计数执行 log(1+x) 后计算波动程度 | 越高表示周间变化更明显 |
| 最长无提交周比例 | 最长连续零提交周数除以 12 | 越高表示存在更长的无提交间隔 |
| 近期变化量 | 最近四周与此前八周均值经 log1p 后的差 | 表示活动相对变化方向和幅度 |
| 前两周集中度 | Commit 量最高的两周总和占 12 周总量的比例 | 越高表示活动更集中在少数周 |

K-Means 先对训练集特征进行标准化，再从不同簇数候选中采用当前课程方案 K=3。标准化参数和簇中心由训练数据拟合；留出仓库使用相同的变换参数和簇中心进行分配。多个随机种子用于检查训练分配是否稳定。簇名依据特征均值作解释性命名，包括“集中活动型”“低活动型”和“持续活动型”，描述的是近期行为，不是仓库质量标签。

#### 3.4.2 M2：未来四周活动趋势分类

M2 根据每个仓库预测时点之前的周级 Commit 历史，分类未来四周相对前四周的活动变化。趋势标签采用规则定义：未来四周 Commit 总数相对此前四周增加或减少，且绝对变化达到 max（3 次 Commit，基期数量的 25%），才分别标为“上升”或“下降”；低于阈值则标为“基本稳定”。该定义兼顾了绝对差异和相对差异，避免将极少量活动变化夸大为趋势。

模型输入包括近期四周的 log Commit 均值、此前八周的 log Commit 均值、活跃周占比、log Commit 波动和近期变化量。候选模型以标准化逻辑回归为主，并比较不同正则强度与类别权重；近期趋势规则和多数类分类器作为基线。类别权重用于减轻三类标签数量不均衡的影响。M2 输出上升、稳定或下降的类别，不预测精确 Commit 数，也不提供未经校准的概率。

#### 3.4.3 样本切分与评估方法

课程模型源数据包含 300 个仓库，每个仓库有 52 周数据，共 15,600 条仓库周记录。固定清单依据 repository_id 将仓库划分为 150 个训练样本和 150 个留出样本，并检查两组没有交集且合计覆盖全部仓库。同一仓库的多个时间窗口不会分到训练集和测试集两侧，以减少仓库信息泄漏。M2 先在训练仓库中进行滚动时间验证，确定参数后再报告留出集指标。

训练与测试采用仓库级留出，但数据来源并非时间上完全独立的新样本，也没有包含新仓库上线后的实际预测结果。前期研究用过同一批 300 个仓库和部分历史窗口，因此这里的结果应理解为历史留仓回测。

## 4 结果与评价

### 4.1 固定仓库样本的描述性统计

course-research-300-v1 包含 300 个仓库的 12 周 UTC 聚合数据。每个仓库的 12 个 Commit 周均处于完整或真实零值状态，共记录 125,246 次提交。PR 合并周中有 3,588 条覆盖完整，另有 12 条因并发变化标记为部分覆盖。系统据此区分窗口内确认的零值与仅有部分观测的情况。

course-research-events-300-v1 还包含约一年的历史事件记录，可用于单仓分析和同期比较。事件量较大并不代表样本具有总体代表性。Issue 数据有明确的采集起点，部分仓库的 PR 或 Release 模块也未完整覆盖；阅读汇总数字时需同时考虑数据窗口和来源说明。

### 4.2 M1 聚类结果

M1 使用 150 个训练仓库拟合 K-Means，并将模型应用于 150 个留出仓库。当前方案设为 3 个簇，评估结果如下：

| 评估项 | 当前结果 | 含义 |
|---|---:|---|
| 训练集轮廓系数 | 0.489 | 衡量训练样本簇内紧密度与簇间分离度 |
| 多随机种子轮廓系数均值 | 0.489 | 本轮不同初始化下的平均训练表现 |
| 留出集轮廓系数 | 0.523 | 留出仓库应用训练后模型得到的簇结构 |
| 按提交规模分组的留出参照 | 0.252 | 检查仅按 Commit 总规模分组的区分度 |
| K=3 训练分配的种子间平均 ARI | 1.000 | 训练分配在本次候选初始化间一致 |
| 留出集簇规模 | 38、28、84 | 分别对应集中活动、低活动和持续活动描述 |

轮廓系数反映特征空间中的簇内紧密度与簇间分离度，不是分类正确率。五特征聚类的轮廓系数高于参照方案，表明分组结构不只由 Commit 总量决定。参照方案仍使用同一批历史样本，属于内部对照，不能视作外部验证。低活动簇可能包含阶段性维护、成熟稳定、临时停更或采集时点不同等情况，活动模式本身不足以判断项目价值。

机器学习观测台以留出仓库的活跃周占比和最长连续无提交周占比作为散点坐标，并用颜色区分模型输出的维护模式。二维投影只显示五项输入特征中的两项，不能完整表达模型计算的距离。多个点重叠时使用的轻微视觉错位仅便于辨认，不会改变预测结果。

### 4.3 M2 分类结果

M2 的留出测试含 150 个仓库，逻辑回归候选采用 C=0.1 和 balanced 类别权重。与近期趋势规则基线及多数类基线相比：

| 模型或基线 | Macro-F1 | 平衡准确率 | 测试仓库 |
|---|---:|---:|---:|
| 逻辑回归候选（C=0.1，类别平衡） | 0.541 | 0.579 | 150 |
| 最近趋势规则基线 | 0.440 | 0.443 | 150 |
| 多数类基线 | 0.222 | 0.333 | 150 |

Macro-F1 是各类别 F1 的平均值，可降低多数类对整体分数的影响；平衡准确率则是各类别召回率的平均值。本次历史留出评估中，模型分数高于两个基线，但对上升类别的召回仍有限。使用结果时应同时查看分类标签、观测窗口和近期 Commit 实际数据。

| 实际类别 | 预测为下降 | 预测为基本稳定 | 预测为上升 | 实际样本数 |
|---|---:|---:|---:|---:|
| 下降 | 19 | 0 | 7 | 26 |
| 基本稳定 | 11 | 51 | 13 | 75 |
| 上升 | 14 | 19 | 16 | 49 |

模型较常识别“基本稳定”类别，下降和上升仍有误判；部分活动实际增加的仓库被预测为稳定或下降。趋势标签表示模型依据当前特征和阈值作出的分类，不是对未来的确定判断。类别阈值由项目规则定义，更改绝对阈值、相对阈值或预测窗口都会改变标签和评估结果。

### 4.4 系统验证与复现方案

系统验证覆盖数据正确性、接口一致性、图表呈现、任务容错和交付复现。项目代码包含后端与前端行为检查，README 列有相应运行命令。本报告不据此推断本次运行中所有检查均已通过。

| 验证类别 | 关注内容 | 核对依据 |
|---|---|---|
| 数据与统计 | UTC 周边界、开闭区间、去重、有效样本、分位数、真实零值与部分覆盖 | 固定样例、原始事件与导出数据复算 |
| API 与业务流程 | 请求字段、失败码、任务进度、比较窗口、模型评估结构 | 后端接口及服务层检查 |
| 图表与页面 | 空态、部分覆盖、样本量提示、图例、响应式布局、导出 | 前端构建、浏览器流程与图表数据断言 |
| 任务与归档 | 重试、幂等性、页数预算、检查点、安全回放 | Worker 状态、归档哈希与固定任务输入 |
| 启动与交付 | 一键启动、数据库迁移、两套页面和本地依赖提示 | 干净环境启动记录和健康检查 |

固定模型评估清单记录数据源哈希、仓库 ID 切分哈希、特征模式版本和测试预测文件。课程模型可以按材料重复构建；若要评估其外部有效性，还需加入未参与前期研究的新仓库，预先锁定预测时间点，再独立观察后续结果。对同一批历史仓库重新随机切分，无法替代这一验证。

### 4.5 结果适用范围与限制

1. **仓库样本存在选择范围。** 300 个课程仓库是既有研究样本，不是 GitHub 全体项目的概率抽样；样本中体现的项目规模和活动结构不一定代表所有仓库。
2. **历史快照不是实时事实。** 固定数据包对应确定的采集日期。线上仓库会继续变化，页面应以实际最近采集时间为准。
3. **GitHub 端点有统计语义限制。** Commit 来自默认分支可见历史，Issue 使用最近可见关闭时间，PR 耗时只对合并记录计算，Release 不包含纯 Tag。不同端点统计不能简单拼成单一质量分。
4. **模型测试不是全新外部验证。** 固定 150 个留出仓库在当前训练中未参与拟合，但其所在 300 仓库集合和部分历史窗口曾用于前期研究。模型性能需要在新的样本中再次验证。
5. **短期活动不能代表长期维护质量。** 活动会受发布周期、仓库成熟度、开发模式、贡献者习惯和项目用途影响。安静的仓库可能稳定运行，活动频繁的仓库也可能处于重构或故障修复阶段。
6. **比较结果依赖选择与权重。** 雷达图按参与比较集合进行归一化；改变仓库集合会改变相对分数。加权排名体现用户指定的指标偏好，不能当作平台对项目的绝对评级。
7. **项目当前以 GitHub 为数据源。** 通用分析架构可继续扩充，但尚未声称支持其他代码托管平台、私有仓库、源代码静态质量评估或安全漏洞审计。
8. **研究模型与生产准入分离。** ML 观测台和单仓研究性模型使用课程研究候选文件；ml-production 受信任目录目前没有批准的生产模型。研究评估分数不能替代外部验收、人工复核和负责人批准。

## 5 总结与展望

本项目实现了面向多类型公开 GitHub 仓库的通用分析工作台，覆盖仓库目录与分组、活动采集、数据质量标记、统计分析、图表比较、机器学习评估和本地启动。平台不以脱离场景的单一“好坏分数”概括仓库，而是并列呈现观察窗口、样本量、覆盖状态和来源范围，供使用者结合项目用途判断。

系统将 Commit、Issue、Pull Request 和 Release 事件转换为统一的 UTC 指标，并区分完整、真实零值、部分覆盖、未采集和失败状态。比较页面分别呈现相对雷达图与可配置权重排名，在分组或语言差异较大时提醒用户核实用途可比性。机器学习部分包括 M1 近期 Commit 节奏聚类和 M2 未来四周活动趋势分类；固定留出样本结果高于本轮基线，但仍受样本来源、历史研究复用和活动分布变化影响，适用于课程研究与观察，不代表所有仓库质量，也未获准用于生产服务。

后续工作可完善多来源采集、覆盖状态和统一比较窗口，开展跨语言、跨规模、跨用途的分层误差分析，并加入全新的外部留出仓库。只有在模型、数据切分和验收证据均可追溯后，才适合评估生产准入。接入其他代码托管服务时，应先将平台特有事件映射到通用指标契约，并明确无法对齐的字段，避免仅凭名称相近就把指标视为等价。
