# 研究分析与技术选型比较：现状问题及改进建议

- **分析日期：** 2026-11-14
- **范围：** 研究分析页、仓库比较能力、课程样本和本机数据库现状
- **分析方式：** 只读检查代码与本机 SQLite 数据；未修改业务代码、数据集或数据库，未触发 GitHub 采集

## 一、结论

研究分析页确实从本地数据库和历史事件快照读取数据，并执行了逐仓库指标计算；但当前展示重点是仓库样本画像、覆盖情况和汇总统计。它能描述“这批仓库有哪些、观察到了什么”，却没有回答“同一用途下哪些仓库可以互相替代、候选之间的取舍是什么、为什么会难以选择”。

现有 300 个仓库主要按机器学习和样本覆盖需求组织，不是按产品用途构建的同类候选组。它们仍适合用于活动特征探索和模型评估，但不能直接作为技术选型比较集。应把“机器学习样本分析”与“同类候选决策分析”作为两个不同的数据与产品问题处理。

## 二、已核对的现状

| 项目 | 当前情况 | 对选型分析的影响 |
|---|---|---|
| 研究页默认数据 | 研究页默认读取 course 模式，即 300 仓库课程样本 | 展示的是样本画像，不是围绕具体决策场景组织的数据 |
| 课程样本结构 | 本机数据库中有 300 个成员，五种语言各 60 个；包含 train/test 角色，测试组 150 个 | 语言和 Stars 分层有利于模型样本覆盖，但没有说明仓库之间是否同类、是否互为替代品 |
| 正式研究集 | 本机数据库的 research-2026-v1 当前为 0 个成员 | 当前默认展示并非来自一个已冻结的正式选型研究集 |
| 现有比较流程 | 比较页可选仓库；候选组和场景字段允许自由填写，前端默认类似“当前所选仓库” | 没有强制比较同一用途或校验候选组口径，用户可能比较不相干的仓库 |
| 可用指标 | 主要包括每周 Commit、Issue 关闭耗时、PR 合并耗时、Release 间隔，以及语言和覆盖信息 | 这些指标主要反映可观察到的维护活动，不能单独证明功能适配、性能、安全或兼容性 |
| 选型反馈 | 本机数据库当前 selection_feedback 为 0 条 | 暂无用户实际选择、选择信心、困难程度和原因可用于验证“难选”判断 |
| 页面分析口径 | 当前相关系数没有计算值，页面明确标注为描述性统计；部分指标基于已观察样本 | 当前不是推断候选差异或判断决策困难的统计分析 |
| 研究分析计算性能 | insights 路径逐仓库读取仓库、采集运行和周统计，存在 N+1 查询形态 | 有额外查询开销风险；尚未做性能测量，需通过批量查询和实测确认影响 |

以上数据库成员数和反馈数来自本机 data/app.db 的只读核对，描述本次检查时的本地状态，不代表所有部署环境或之后的数据状态。

## 三、现有页面为什么像摘要

研究页当前把若干指标聚合为样本总量、语言构成、Commit 活动、Issue/PR/Release 中位数和覆盖状态。计算真实读取了本地数据库及事件快照，因此问题不在于“没有查数据库”，而在于：

1. **问题定义偏向描述样本。** 页面没有先确定某项技术需求或使用场景，再围绕场景组织候选。
2. **样本关系缺失。** 数据集记录仓库及 train/test 等成员属性，但没有维护同类用途、候选组、替代关系和纳入依据。
3. **比较口径未约束。** 现有比较可以对多个仓库加权，但缺少同类候选的校验，也没有要求统一指标窗口和数据覆盖。
4. **指标与决策结论不匹配。** 活跃度和维护节奏可以提供维护信号，不能替代功能契合度、运行性能、兼容性、安全性等选型依据。
5. **缺少“难以抉择”的验证标签。** 目前没有选择难度、决策信心、最终选择和选择理由的反馈数据，无法验证系统识别出的困难是否符合真实用户感受。

## 四、机器学习样本与选型候选集应分开

300 仓库样本是按语言和规模分层的宽覆盖样本，目标是支持课程研究、活动特征分析和机器学习实验。它不是 GitHub 总体的概率样本，也没有按具体用途组成同类组。因此：

- 不应把 300 个仓库直接当成一个可供所有场景筛选的候选池。
- 不应把 train/test 留出角色解释为候选之间的对照关系；留出评估和产品选型解决的是不同问题。
- 不应因为某类候选不足，就用不同功能的仓库补齐比较组。
- 现有数据仍可用于维护活动描述、模型特征探索和数据管道验证；对于选型价值，需要补上明确的场景、候选关系和决策证据。

一次基于 topic 和简介的快速检索中，“Web 框架”在当前 300 个样本里只有 gin-gonic/gin 一个明确命中。此检索只是快速文本筛查，不是完整人工分类；它体现的是候选组需要审查和补充，不能据此宣称样本中完全没有其他相关项目。

## 五、建议的目标数据与分析

### 1. 建立版本化的选型场景与候选组

每个候选组至少记录：

- 场景名称和功能类别，例如某语言下的 Web 框架或任务队列。
- 用户需求和硬性约束，例如语言、运行环境、许可证、部署方式和最低功能要求。
- 候选仓库及其纳入理由、维护状态和人工复核时间。
- 数据来源、采集截止时间、指标窗口和每个指标的覆盖状态。
- 适用和不适用的证据范围，以及尚未采集的指标。

候选组采用独立版本标识和变更记录。先盘点现有 300 个样本中是否有至少两个真实可比的候选；不足时再围绕明确场景补充候选，不把 ML 样本设计改造成选型设计。

### 2. 将“难以抉择”作为需要证据支持的结论

可以先用两类信号发现潜在的困难场景：

- **客观取舍：** 多个候选各自在不同维度占优，没有一个候选在所有已测维度上都更好；或用户权重稍有变化，推荐结果就发生变化。
- **用户反馈：** 记录选择难度、选择信心、最终选择、关键原因和未满足需求，并允许用户跳过反馈。

客观信号用于提出“值得比较”的候选组，用户反馈用于检查这些场景是否真的让人难选。系统应说明判断依据，不把 Stars 高、分数接近或算法排序不稳定直接等同于用户难以抉择。

### 3. 先筛硬条件，再展示多维取舍

把必要条件作为候选过滤项，把维护、社区活动等作为可观察信号；功能覆盖、性能、安全和兼容性只在有相应数据时纳入。候选结果应展示各维度的原始证据、缺失情况、指标时间窗和权重变化影响，不只显示一个不透明的总分或胜者。

统计比较应限定在同一场景、同一观察窗口和可比的覆盖口径。报告每组的候选数、样本量、分布或区间、差异幅度及不确定性。样本不足或覆盖不一致时，明确标注“证据不足”，不做强结论；避免仅凭 p 值或相关性声称因果关系。

### 4. 明确当前数据的边界

当前事件快照没有提交说明、Issue / PR 标题和正文，部分采集模块也存在部分覆盖。因此它适合回答有限的 GitHub 活动问题，不足以回答完整的产品功能问题。功能契合需要结构化功能信息或人工需求评估；性能需要可比基准；安全需要漏洞或审计数据；兼容性需要运行环境和依赖证据。引入这些结论前，应先确定来源、采集规则和质量口径。

## 六、研究分析页面的建议结构

将页面从“先显示全样本摘要”调整为“先选决策问题，再看比较证据”：

1. **场景与约束：** 选择功能类别、技术栈和硬性要求。
2. **候选集说明：** 展示候选数量、纳入理由、数据截止日期和覆盖情况。
3. **候选差异：** 并列展示满足条件情况、维护信号、证据范围和差异；说明各自的优势与代价。
4. **困难度依据：** 展示取舍冲突、权重敏感性和用户反馈，明确区分自动计算结果与实际用户意见。
5. **证据与限制：** 可展开查看指标口径、数据缺失、观察窗口和不可推断的内容。

图表应服务于具体问题，而不是继续堆叠摘要指标。例如用分布图展示候选表现重叠，用并列差异图显示维度取舍，用时间序列展示维护变化，并单独展示数据覆盖。图表形式本身不能弥补候选组和指标证据的缺失。

## 七、建议的实施顺序与验收标准

### 阶段一：候选盘点与场景试点

- 对现有 300 个仓库按明确的功能类别做人工复核，记录候选组数量和不足。
- 选择一个现有数据能支撑的窄场景试点；如果没有足够同类候选，先补充样本。
- 冻结候选组规则、指标口径、时间窗和纳入理由。

**验收：** 试点组至少有两个经复核的同类候选；每个候选有一致的观察窗口、可追溯来源和明确覆盖状态。

### 阶段二：比较分析与页面验证

- 先实现硬条件筛选和候选维度对比，再决定哪些统计结论具有足够样本支持。
- 加入证据缺失提示、解释文本和权重敏感性分析。
- 对研究统计路径进行批量查询优化，并测量优化前后的查询数和响应时间。

**验收：** 用户能看出候选为何入组、哪些指标不同、差异可能意味着什么、哪些结论目前不能下；同一条件下结果可复现。

### 阶段三：收集真实决策反馈

- 在不强迫用户提交的前提下收集难度、信心、最终选择和理由。
- 将反馈用于验证候选困难度识别，不把反馈标签与 ML 的 train/test 划分混用。

**验收：** 页面可以区分模型或规则识别的潜在取舍与用户实际报告的决策困难，并能追溯反馈对应的场景和候选版本。
