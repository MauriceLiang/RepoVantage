### 实现

- `backend/app/analytics/course_ml_features.py` 从最近 8 个连续完整 UTC 周计算此前 4 周与最近 4 周的真实 Commit 数。显著变化阈值为 `max(3, previous4 × 25%)`；覆盖不足时返回无法判定，不补零。
- 详情、仓库对比和 Markdown 选型报告均分开标注“最近 4 周实际变化”与“未来 4 周活动趋势预测”。M2 只展示类别与预测 UTC 窗口，不展示概率或预测 Commit 数；不适用时保留原因。
- `backend/app/services/ml_evaluation.py` 和 `backend/app/schemas/ml_evaluation.py` 将事实变化作为可选结果字段供页面使用。

### 验证结果

- 单测覆盖显著上升/下降、稳定、全零、`0 → 1`、`0 → 4`、缺周和日期窗口。

- CPython 示例：最近 `681`、此前 `410`，显示“近期上升”；M2 独立显示未来预测“下降”。
- 对比页和 Markdown 报告预览中，两类语义、计数及 UTC 窗口分别呈现。

## 3. T3：控制课程版 Commit 分页预算

### 实现

- `backend/app/services/maintenance_collection.py` 集中设置默认 20 页预算，Worker 复用同一常量。
- 审计记录页数、预算耗尽状态、来源及估算 GitHub 请求数。完整缓存命中时 Commit 分页数为 0，且预算调低不会废弃可信缓存。
- 超过预算仍有下一页时保留已观察的下界事实并标为 partial；依赖完整 Commit 特征的 M1/M2/M3 不输出结果。PR 覆盖独立处理。

### 验证结果

- 受控分页测试验证 20 页内可完成、总计超过 20 页时仅读取 20 页并 partial、局部数据不进入模型；请求估算为 35 次（含 20 次 Commit 页与其它固定估算项）。
- 受控完整缓存测试验证页预算为 20、Commit 请求页数为 0、缓存命中。
- v4.1 留存的真实 GitHub 证据中，Hello-World 重复 12 周采集命中缓存，新增请求为 0；该证据来自预算调整前。本轮没有对 GitHub 发起新的线上采集。
- v4.1 的 Linux 真实记录为 100 页、约 115 次请求估算并以 partial 结束。v4.2 受控测试将读取上限证明为 20 页、估算 35 次；由于未对同一 Linux 仓库重跑，不把两条记录宣称为同仓库实测节省量，也不外推所有仓库的请求节省。
